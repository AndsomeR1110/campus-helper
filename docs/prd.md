# 1. 项目概述（Product Overview）

## 1.1 项目背景

大学生在校园生活中需要使用不同的网站、平台和应用处理学习及日常事务。例如：

- 查询教师的 Office Hour。
- 查找和预约学习座位。
- 管理课程时间和上课提醒。
- 发布失物招领信息。

这些活动通常需要经过不同的操作流程，增加了学生的信息查找与任务管理成本。

CAMPUS HELPER 旨在通过一个统一的平台，整合上述高频校园服务，并提供简洁、直观、面向移动设备的使用体验。

本项目以 PWA 作为主要实现形式，使学生既可以通过浏览器访问，也可以将应用添加到手机主屏幕。

## 1.2 产品愿景

构建一个简单、易用的数字校园助手，使学生能够通过一个平台高效完成日常校园任务。

**产品核心价值：**

1. Convenience：减少在不同系统之间切换。
2. Efficiency：简化校园服务的操作流程。
3. Organization：统一管理课程、预约及提醒。
4. Community：促进学生之间的失物招领互助。

## 1.3 项目目标

本毕业设计的主要目标：

- 设计一套完整且一致的移动端 UI/UX。
- 开发具备实际数据交互能力的 Web App。
- 实现四项核心业务功能。
- 建立用户认证、数据库和基础角色权限系统。
- 实现 PWA 安装、响应式布局和基础离线处理。
- 完成系统测试、用户体验评估及项目文档。
- 将系统部署到可通过 HTTPS 访问的测试环境。

本项目不要求获得学校官方系统的接口授权。

## 1.4 成功标准

| 指标               | 毕业设计目标                         |
| ------------------ | ------------------------------------ |
| 核心功能覆盖率     | 四项核心功能全部可演示               |
| P0 需求验收        | 100% 通过                            |
| 核心任务完成率     | 10 名以上测试者中达到 90%            |
| 严重安全或数据错误 | 0 个未解决的关键问题                 |
| PWA 部署           | 可通过 HTTPS 使用并安装到支持的设备  |
| 数据持久化         | 刷新、退出重登后核心数据保持一致     |
| 学术交付           | 完整需求、设计、实现、测试和评估材料 |

以上为预设目标，而非已经取得的测试结果。

# 2. 产品范围（Product Scope）

## 2.1 MVP 必须实现的模块（P0）

**基础系统**

- 用户登录、注册、退出。
- 学生、教师和管理员角色。
- Home、Services、Schedule、Profile 四个主要导航入口。
- 统一的预约记录和站内通知。

**Office Hour Booking**

- 搜索和查看教师。
- 查看开放时段。
- 创建、查看、取消预约。
- 教师管理自己的可预约时段。

**Study Space Booking**

- 查看演示图书馆空间及座位。
- 根据日期、时间、区域筛选。
- 创建和取消预约。
- 防止同一座位同一时间被重复预约。

**Class Reminder**

- 手动创建、编辑、删除课程。
- 展示每周课表。
- 设置课前提醒。
- 查看即将到来的课程。
- 支持导出课程日历文件。

**Lost & Found**

- 发布遗失或拾获物品。
- 上传物品图片。
- 搜索和筛选帖子。
- 发起认领申请。
- 确认认领及关闭帖子。
- 基础举报和内容审核。

**PWA**

- 可安装的应用 Manifest。
- Service Worker。
- 基础离线页面。
- 通知权限管理和支持平台上的 Web Push。
- 移动端响应式设计。

## 2.2 第二阶段功能（P1）

- 中英文界面切换。
- 预约改期。
- 高级日历文件导入。
- 更丰富的课程重复规则。
- 失物招领站内实时聊天。
- 空间收藏和评价。
- 校园楼宇导航链接。
- 高级通知偏好设置。

## 2.3 暂不实现（Out of Scope）

- 真实学校教务系统同步。
- 实时图书馆官方空位监控。
- 学校统一身份认证 SSO。
- 与学校正式预约系统的写入式集成。
- AI 图像识别与失物自动匹配。
- 精确室内定位。
- 在线支付。
- 原生 iOS/Android 应用开发。

特别说明：本项目使用独立维护的演示教师、课程和学习空间数据。系统应明确标记为学术项目，不得让测试用户误认为预约结果已写入学校官方系统。

# 3. 目标用户与权限（Users & Roles）

## 3.1 学生（Student）

学生是主要用户。

**典型场景：**

- 希望预约教师进行课程答疑。
- 希望找到可以学习的座位。
- 希望及时收到上课提醒。
- 希望找回遗失物品。

**核心需求：**

操作简单、信息清楚、预约可靠、通知及时。

## 3.2 教师（Teacher）

教师通过专用管理界面：

- 创建 Office Hour 时段。
- 查看预约名单。
- 取消未开始的时段。
- 查看相关预约状态。

教师账号由项目管理员预先创建或赋予权限；普通学生不得自行切换为教师角色。

## 3.3 管理员（Administrator）

管理员负责：

- 管理演示用户。
- 管理演示学习空间。
- 审核和隐藏失物招领帖子。
- 处理举报。
- 查看系统基础运行状态。

## 3.4 权限矩阵

| 功能                 | Student | Teacher | Admin      |
| -------------------- | ------- | ------- | ---------- |
| 查看教师与可预约时段 | 是      | 是      | 是         |
| 创建学生预约         | 是      | 否      | 按管理权限 |
| 管理教师时段         | 否      | 仅自己  | 是         |
| 预约学习空间         | 是      | 可选    | 是         |
| 管理个人课表         | 是      | 可选    | 是         |
| 发布失物招领         | 是      | 可选    | 是         |
| 审核和隐藏帖子       | 否      | 否      | 是         |
| 管理用户权限         | 否      | 否      | 是         |

## 4.3 全局页面交互规范

所有页面应遵循以下规则：

- 使用统一的顶部标题和返回入口。
- 学生主页面显示底部导航。
- 重要操作必须提供明确的成功或失败反馈。
- 网络请求过程中显示 Loading 状态。
- 列表为空时显示 Empty State。
- 网络异常时提供 Error State 和重试按钮。
- 需要用户确认的取消、删除操作使用确认弹窗。
- 不允许点击无效按钮后毫无反馈。
- 手机浏览器和安装后的 PWA 应采用一致的布局和交互逻辑。

# 5. 核心用户流程（User Flows）

## Flow 01：预约教师

登录 → Services → Office Hour → 搜索教师 → 查看可预约时段 → 选择时段 → 填写主题 → 确认预约 → 显示成功 → 在 My Bookings / Schedule 中查看。

**异常流程：** 当时段已被预约、已过期或者教师取消开放时，应阻止预约并显示原因。

## Flow 02：预约学习空间

登录 → Find Space → 选择日期及时间 → 筛选楼宇/楼层 → 查看可用座位 → 选择座位 → 确认预约 → 查看预约详情。

**异常流程：** 当座位在提交时被其他用户预约，系统应提示冲突并允许重新选择座位。

## Flow 03：课程提醒

登录 → Schedule → 添加课程 → 填写课程信息和教学周 → 设置提醒 → 保存 → 课程显示在课表 → 到达提醒时间生成通知。

**异常流程：** 当用户拒绝浏览器通知权限时，应用仍应保留站内通知，并提供日历导出作为备用方案。

## Flow 04：失物招领

登录 → Lost & Found → 发布 Lost/Found → 填写信息 → 发布成功 → 其他用户浏览 → 提交认领申请 → 发布者核对 → 确认归还 → 标记 Resolved。

**异常流程：** 帖子被隐藏、删除或已解决后，不允许再创建新的认领申请。

# 7. 功能详细需求与验收标准

本节是 PRD 最重要的部分。每项需求均提供：功能编号（FR）、业务规则、验收编号（AC）、可验证的操作与预期结果。

## 7.1 用户认证与首页

### 功能需求

**FR-AUTH-01：用户登录** — 支持测试账号通过邮箱和密码登录。登录成功后进入 Home。

**FR-AUTH-02：用户注册** — 支持创建普通 Student 账号，完成字段校验。教师及管理员角色不得通过公开注册获取。

**FR-AUTH-03：访问权限** — 未经登录不能访问受保护的业务页面；不同角色只能访问授权资源。

**FR-HOME-01：首页信息** — 首页显示用户名称、下一节课、服务入口及最近的有效预约。没有数据时显示适当的空状态。

### 验收标准

| AC ID      | 测试场景与预期结果                                         |
| ---------- | ---------------------------------------------------------- |
| AUTH-AC-01 | 输入有效测试账号和密码，点击登录后成功进入 Home。          |
| AUTH-AC-02 | 输入错误密码，系统拒绝登录并显示错误，不泄露敏感认证信息。 |
| AUTH-AC-03 | 未登录直接访问预约页面，系统要求登录。                     |
| AUTH-AC-04 | 普通学生尝试访问教师或管理员功能，服务器拒绝授权。         |
| AUTH-AC-05 | 用户刷新 Home，登录状态有效时仍能查看个人数据。            |
| HOME-AC-01 | 用户存在未来课程时，首页正确显示时间最近的一节课。         |
| HOME-AC-02 | 用户没有课程或预约时，首页显示空状态且不报错。             |

## 7.2 Office Hour Booking

### 功能需求

**FR-OH-01：教师搜索** — 学生可以通过教师姓名或所属课程等字段搜索教师。

**FR-OH-02：教师资料** — 展示教师姓名、所属部门、课程信息及可预约时段。

**FR-OH-03：时段管理** — 教师能够创建未来时段，设置开始时间、结束时间和地点。MVP 规定：一个预约时段默认只能被一名学生预约。

**FR-OH-04：预约创建** — 学生选择有效时段并填写交流主题后，可以提交预约。

**FR-OH-05：预约取消** — 学生可以取消未开始的预约，取消后时段重新开放（前提是教师未撤销该时段）。

**FR-OH-06：教师取消** — 教师可以撤销未来的开放时段。对于已有预约，系统同步更新状态并通知对应学生。

**FR-OH-07：统一日程** — 确认后的 Office Hour 预约显示在 My Bookings 和 Schedule 中。

### 业务约束

- 不允许预约过去的时段。
- 同一时段不能超额预约。
- 同一学生不能重复预约同一时段。
- 仅时段所属教师可以修改该时段。
- 预约状态由后端确认，不能只根据前端按钮状态判断。
- 预约取消应保留历史记录用于演示与测试。

### 验收标准

| AC ID    | 测试场景与预期结果                                               |
| -------- | ---------------------------------------------------------------- |
| OH-AC-01 | 输入教师姓名关键词后，列表只显示匹配教师。                       |
| OH-AC-02 | 选择一个有效开放时段并提交，系统创建 Confirmed 预约。            |
| OH-AC-03 | 两名学生同时预约最后一个名额，只有一人成功；另一人收到冲突提示。 |
| OH-AC-04 | 学生尝试再次预约同一时段，系统阻止重复预约。                     |
| OH-AC-05 | 学生取消未来预约后，个人状态变为 Cancelled，对应时段恢复可预约。 |
| OH-AC-06 | 教师创建时段后，学生端可以看到该时段。                           |
| OH-AC-07 | 教师撤销已有预约的时段，预约状态同步更新且生成通知。             |
| OH-AC-08 | 预约成功后，Home、Schedule 和 My Bookings 显示一致的数据。       |

## 7.3 Study Space Booking

### 功能需求

**FR-SP-01：空间列表** — 显示演示图书馆空间，包括：校区、楼宇与楼层；空间或座位编号；座位类型；是否支持讨论；容量、插座等设施信息。

**FR-SP-02：空间筛选** — 学生可以按楼宇、楼层、类型、日期和时间筛选座位。

**FR-SP-03：时段可用性** — 根据指定开始和结束时间，计算座位在该时段是否可预约。可用性不能仅通过数据库中静态的 Available 布尔值判断。

**FR-SP-04：创建预约** — 学生选择座位及时间，提交预约并获得确认结果。

**FR-SP-05：取消预约** — 学生可以取消尚未开始的预约。

**FR-SP-06：预约记录** — 座位预约显示在 My Bookings 和 Schedule 中。

### 建议的演示预约规则

- 预约时间粒度：30 分钟。
- 单次预约时长：30–180 分钟。
- 可预约范围：未来 7 天。
- 同一学生在重叠时间内最多保留一个有效座位预约。
- 已开始或过去的预约不能直接取消。
- 预约状态与规则全部由后端验证。

这些规则是毕业设计的演示规则，不代表真实学校图书馆政策。

### 验收标准

| AC ID    | 测试场景与预期结果                                       |
| -------- | -------------------------------------------------------- |
| SP-AC-01 | 选择楼层及座位类型后，结果按所选条件过滤。               |
| SP-AC-02 | 选择不同日期或时间，座位可用状态随预约数据变化。         |
| SP-AC-03 | 选择符合规则的空闲座位并提交，系统成功创建预约记录。     |
| SP-AC-04 | 两名学生提交重叠的同一座位预约，只能成功一个。           |
| SP-AC-05 | 尝试预约过去日期或超出时长限制，系统拒绝提交并说明原因。 |
| SP-AC-06 | 取消尚未开始的预约后，座位在对应时间段重新可预约。       |
| SP-AC-07 | 所有演示座位均清楚标注为非学校官方实时数据。             |
| SP-AC-08 | 预约完成后可在 My Bookings 及 Schedule 中正确查看。      |

## 7.4 Class Reminder

### 功能需求

**FR-CR-01：创建课程** — 学生可以填写：Course Code、Course Name、Teacher（选填）、Classroom / Building、Weekday、Start Time、End Time、Teaching Weeks、Reminder Time。

**FR-CR-02：编辑与删除课程** — 学生能够修改课程信息、删除课程，并使未来课程日程和提醒同步更新。

**FR-CR-03：周课表展示** — 支持周视图及列表视图，并高亮当前日期。

**FR-CR-04：课程提醒** — 默认提前 15 分钟，可选择关闭、提前 10、15、30 或 60 分钟。

**FR-CR-05：统一日程** — Schedule 显示课程和预约事件，使用不同图标或视觉样式区分类型。

**FR-CR-06：日历导出** — 学生能够将课程安排导出为标准 `.ics` 文件，供兼容的设备日历应用导入。

### 业务规则

- 课程结束时间必须晚于开始时间。
- 保存的课程不得产生无效的教学周或日期。
- 课程时间按 `Asia/Shanghai` 时区处理；服务端统一存储明确的时间信息。
- 重复提醒必须考虑教学周范围。
- 修改或删除课程后，旧提醒任务不得继续错误触发。
- 服务器负责生成站内提醒，避免依赖用户保持网页打开。
- Web Push 仅在设备、浏览器及用户授权支持时发送。
- 不允许相同事件和提醒规则造成重复通知。

### 验收标准

| AC ID    | 测试场景与预期结果                                         |
| -------- | ---------------------------------------------------------- |
| CR-AC-01 | 输入合法课程信息并保存，课程出现在对应周次与星期的课表中。 |
| CR-AC-02 | 输入结束时间早于开始时间，表单阻止保存并提示错误。         |
| CR-AC-03 | 编辑课程地点或时间后，课表和未来提醒同步更新。             |
| CR-AC-04 | 删除课程后，相关未来课程事件和提醒不再出现。               |
| CR-AC-05 | 设置提前 15 分钟提醒，到达约定时间时系统生成一条站内通知。 |
| CR-AC-06 | 重复执行提醒任务，不应为相同课程事件产生重复通知。         |
| CR-AC-07 | 用户拒绝浏览器通知权限，仍能查看站内通知及导出日历。       |
| CR-AC-08 | 导出的 `.ics` 文件能由选定的兼容日历软件正确识别时间。     |

## 7.5 Lost & Found

### 功能需求

**FR-LF-01：帖子类型** — 提供 Lost（遗失）和 Found（拾获）两种类型。

**FR-LF-02：创建帖子** — 发布时填写：Title、Lost / Found、Category、Location、Date / Time、Description、Image（选填）。物品分类包括：电子设备、校园卡、钥匙、书籍、衣物、其他。

**FR-LF-03：搜索与筛选** — 支持通过关键词、物品分类、帖子类型和地点进行筛选。

**FR-LF-04：帖子详情** — 显示物品图片、公开描述、时间、地点、状态和认领按钮。

**FR-LF-05：认领申请** — 用户提交私密认领说明，描述能帮助验证所有权的特征。该说明只对帖子发布者和授权管理员可见，不对其他学生公开。

**FR-LF-06：认领处理** — 发布者可以接受或拒绝认领申请，并在物品完成归还后标记 Resolved。

**FR-LF-07：帖子管理** — 用户可以查看并管理自己的发布记录。

**FR-LF-08：举报与审核** — 用户可举报不当内容；管理员可查看举报并隐藏帖子。

### 业务规则

- 帖子默认处于 Open 状态。
- 已解决或关闭的帖子不能继续接受新认领。
- 非发布者不能修改其他人的帖子。
- 非授权用户不能查看私密认领信息。
- 上传图片需限制文件类型、大小和数量。
- 不公开展示身份证号、完整学号、电话号码等敏感信息。
- 物品归还应优先使用安全的线下核验方式。
- 第一版不实现实时聊天，使用认领申请和状态反馈完成业务流程。

### 验收标准

| AC ID    | 测试场景与预期结果                                            |
| -------- | ------------------------------------------------------------- |
| LF-AC-01 | 填写合法的 Lost 或 Found 信息后，帖子成功发布并出现在列表中。 |
| LF-AC-02 | 必填字段为空时，系统阻止发布并标记错误字段。                  |
| LF-AC-03 | 上传不支持的图片类型或超出限制大小的图片，系统拒绝文件。      |
| LF-AC-04 | 根据关键词、类型或分类筛选后，显示正确帖子。                  |
| LF-AC-05 | 非发布者可以向 Open 状态帖子提交认领申请。                    |
| LF-AC-06 | 未授权用户无法读取其他用户提交的私密认领说明。                |
| LF-AC-07 | 发布者确认认领并标记 Resolved 后，帖子状态更新并禁止新认领。  |
| LF-AC-08 | 普通用户无法编辑或删除他人的帖子。                            |
| LF-AC-09 | 用户举报帖子后，管理员能看到举报并执行审核操作。              |

# 8. 统一日程与通知

这是 CAMPUS HELPER 区别于四个独立功能页面的重要设计。

## 8.1 统一日程

Schedule 应汇总三类事件：

1. Class：课程。
2. Office Hour：教师预约。
3. Study Space：学习空间预约。

每个事件应包含：事件类型、标题、日期与起止时间、地点、来源记录 ID、业务状态。点击事件后进入对应详情。

## 8.2 通知类型

| 通知事件                 | 触发条件               |
| ------------------------ | ---------------------- |
| Class Reminder           | 到达设定的课程提醒时间 |
| Office Booking Confirmed | 预约成功               |
| Office Booking Cancelled | 预约被取消             |
| Space Booking Confirmed  | 座位预约成功           |
| Booking Reminder         | 预约开始前达到设定时间 |
| Lost & Found Claim       | 收到新的认领申请       |
| Claim Status Updated     | 认领申请状态发生改变   |

## 8.3 通知验收

**NT-AC-01：** 有效业务事件能够生成对应站内通知。

**NT-AC-02：** 通知仅对正确的接收用户可见。

**NT-AC-03：** 重复处理相同事件不产生重复通知。

**NT-AC-04：** 点击通知可进入相关详情，已删除的目标要有合理错误处理。

# 9. 数据需求（Data Requirements）

本 PRD 先定义业务实体，详细字段类型、索引和关联将在数据库设计文档中确定。

| 数据实体         | 核心内容                 |
| ---------------- | ------------------------ |
| User             | 用户身份、角色、账户状态 |
| TeacherProfile   | 教师公开资料             |
| OfficeSlot       | 教师开放预约时段         |
| OfficeBooking    | 学生 Office Hour 预约    |
| Space            | 学习空间与座位           |
| SpaceBooking     | 空间预约时间及状态       |
| Course           | 用户课程信息             |
| CourseOccurrence | 具体课程事件与例外日期   |
| ReminderRule     | 提醒类型与提前时间       |
| LostFoundPost    | 失物招领帖子             |
| LostFoundClaim   | 认领申请及处理状态       |
| Notification     | 站内通知与发送记录       |
| Report           | 用户举报                 |
| AuditLog         | 重要管理操作记录         |

## 9.1 状态设计

**OfficeBooking：** Confirmed → Completed；Confirmed → Cancelled

**SpaceBooking：** Confirmed → Completed；Confirmed → Cancelled；Confirmed → Expired

**LostFoundPost：** Open → Claim Pending → Resolved。另允许 Open → Closed，以及经过审核后进入 Hidden 状态。

**LostFoundClaim：** Pending → Approved / Rejected

状态更新必须由服务端检查合法性，不能由客户端随意传入最终状态。

## 9.2 数据完整性

- 所有记录具有唯一 ID。
- 用户相关记录必须与有效用户关联。
- 预约时间不能出现无效区间。
- 并发预约使用数据库事务和适当的约束或锁。
- 被取消的预约保留状态历史，而不是简单删除。
- 用户只能读取被授权的数据。
- 演示数据必须与真实校园业务数据区分。

## 10.2 PWA 必备要求

| PWA-AC-02 | 从手机主屏幕启动应用，显示适当的独立应用界面。                 |
| PWA-AC-03 | 断开网络后，应用显示可理解的离线状态，不出现空白或无限加载。   |
| PWA-AC-04 | 断网提交预约时，不显示虚假的预约成功结果。                     |
| PWA-AC-05 | 在支持 Web Push 的设备上，用户主动授权后可以接收测试推送。     |
| PWA-AC-06 | 不支持 Web Push 或权限被拒绝时，核心功能及站内通知仍可使用。   |
| PWA-AC-07 | 部署网站使用 HTTPS，Manifest 与 Service Worker 正常加载。      |

# 11. 非功能需求（Non-Functional Requirements）

## 11.1 性能

- 主要业务页面应在正常测试网络条件下快速加载。
- 首次加载应避免不必要的大型依赖和图片。
- 列表查询使用分页或合理的数据量限制。
- 重要交互提供 Loading 状态，防止重复提交。

**性能测试目标：** 使用统一测试环境和固定测试数据，主要页面 LCP 目标不高于 2.5 秒；未达到时应记录原因和优化措施。

## 11.2 响应式与可访问性

至少测试以下视口：375px 手机、768px 平板、1280px 桌面。

验收要求：

- 重要内容不发生水平溢出。
- 底部导航不遮挡主要按钮。
- 表单能通过键盘操作。
- 交互控件具备可理解的标签。
- 错误信息不只依赖颜色区分。
- 文字与背景保持可读对比度。

## 11.3 安全

- 密码不得以明文存储。
- 使用安全的登录会话和 Cookie 配置。
- 所有关键权限由服务端检查。
- 预约和认领接口必须验证当前用户身份。
- 文件上传执行类型、大小和访问权限检查。
- 对登录、发布和认领接口采用基本频率限制。
- 敏感信息不得进入公开页面或浏览器缓存。
- 记录重要管理操作用于问题排查。

## 11.4 可靠性

- 数据库异常时返回明确错误。
- 重复提交不能产生重复预约。
- 服务端处理错误时不能返回虚假的成功状态。
- 后台通知任务具备基本日志和失败处理。
- 提供数据库备份和演示数据恢复方法。

## 11.5 代码质量

- 使用统一 ESLint / Formatter 规则。
- TypeScript 不应存在未解释的大量类型错误。
- 核心业务规则具有自动化测试。
- 关键模块使用清晰的文件和模块划分。
- 所有环境密钥存放在环境变量中。
- Git 仓库不得提交真实密钥。

# 12. 测试计划（Testing Strategy）

## 12.1 测试层级

**Unit Tests：** 测试时间计算、预约冲突规则、字段校验、提醒时间计算以及权限判断。

**Integration Tests：** 测试 API、数据库事务、用户身份和预约状态更新。

**End-to-End Tests：** 使用浏览器自动执行实际用户流程。

**Usability Tests：** 邀请真实学生通过可用性测试脚本完成任务，记录问题。

## 12.2 必须覆盖的端到端场景

- **TC-01：** 学生注册、登录、退出并重新登录。
- **TC-02：** 学生搜索教师、预约 Office Hour、查看并取消预约。
- **TC-03：** 两个学生同时预约同一时段，验证无超额预约。
- **TC-04：** 学生筛选学习座位、预约、查看并取消。
- **TC-05：** 两个学生预约冲突座位时间，验证只有一个成功。
- **TC-06：** 学生创建课程、编辑课程、查看周课表。
- **TC-07：** 系统产生正确的课程提醒，且重复任务不会造成重复通知。
- **TC-08：** 学生发布失物、另一个学生提交认领、发布者确认解决。
- **TC-09：** 普通用户不能访问他人的私密认领申请。
- **TC-10：** 在手机上安装 PWA，验证断网提示与恢复联网后的正常使用。

## 12.3 测试账号与演示数据

建议准备：

- Student A：包含课程、预约与失物帖子。
- Student B：用于模拟预约竞争和物品认领。
- Teacher A：包含多个可预约 Office Hour 时段。
- Administrator：用于审核、数据和管理功能演示。

准备约 20 个演示座位、6–10 门课程、10–15 条失物招领帖子及若干教师时段。

所有演示数据应采用虚构身份或获得明确同意的测试数据。

# 14. 毕业答辩演示流程

建议准备一份约 8–10 分钟的系统演示，具体时长以课程要求为准。

1. **产品概览：** 展示登录页面、首页、四个功能入口及移动端布局。
2. **Office Hour：** 通过 Student A 搜索并预约教师；切换到 Teacher A 查看预约。随后使用 Student B 测试冲突预约。
3. **Study Space：** 选择座位和时间，完成预约；演示座位不可重复预约以及取消后的状态更新。
4. **Class Reminder：** 创建课程，查看课表并展示一次测试提醒。说明 Web Push 与站内通知的区别。
5. **Lost & Found：** Student A 发布物品；Student B 申请认领；Student A 审核认领并标记已解决。
6. **PWA：** 在手机主屏幕启动应用，演示响应式布局、安装体验和断网提示。
7. **技术展示：** 介绍系统架构、数据库实体、权限控制、并发处理、自动化测试与已知限制。

正式答辩前应为演示准备固定种子数据和恢复脚本，避免现场网络或数据问题影响展示。

# 15. 完成定义（Definition of Done）

某项 P0 功能只有同时满足以下条件，才可标记为完成：

1. 页面符合经过确认的设计规范。
2. 前后端接口已连接。
3. 数据能够正确持久化。
4. 角色权限得到验证。
5. 正常和异常流程均有合理反馈。
6. 对应验收标准已经通过。

# 16. 风险与限制（Risks & Limitations）

| 风险             | 影响                     | 应对措施                   |
| ---------------- | ------------------------ | -------------------------- |
| 无学校官方接口   | 不能完成真实学校预约     | 使用明确标识的演示数据     |
| PWA 推送兼容性   | 部分设备无法接收后台推送 | 站内通知 + 日历导出        |
| 预约并发冲突     | 可能重复分配同一资源     | 服务端事务与数据库约束     |
| 项目时间有限     | 所有功能难以同时完善     | 严格按 P0/P1 分级          |
| 失物招领信息敏感 | 可能泄露个人资料         | 隐私字段隔离与审核         |
| 课程时间复杂     | 重复课程提醒可能出错     | 统一时区与重复事件测试     |
| 答辩环境不稳定   | 演示过程出现网络问题     | 固定种子数据与备用演示视频 |
