## 按依赖推进

1. **同步计划（本 PR）**：所有 Agent 先读本文件、任务清单和能力交接。新功能是 PRD 增量；SH/ROOM/AMS 的编号是补充验收编号，不冒充现有 PG/AC。
2. **Codex 发布接入基础**：保留原 worktree；已在原功能分支同步最新 main 并保留 Claude 的新布局，后续整理为可评审提交。拆出原生壳/适配器和 UI facade 的 Draft PR，交付可安装 APK、公开类型及无凭证 fixtures。不要要求 Claude 从未经提交的本地文件复制代码。
3. **Claude 可立即做 UI 设计与预览**：从最新 main 开 UI 分支，先做服务入口和可审查的 UI 状态。稳定公共 facade 之前仅通过模块内预览 adapter 使用 fixtures；不要自创真实接口实现。Codex 发布 facade 后再对齐类型与 import。
4. **区间车纵向交付**：Claude 的页面调用已发布 facade；Codex 接真实链路并验证，再回传截图与差异。共享页面由 Claude 的布局主导，旧原型不得整文件覆盖。
5. **太仓讨论室纵向交付**：先 UI + 只读查询；再做选时/人数/确认；真实创建和取消须在本人及合法组员可参与时另行安排。原先授权仅限不提交讨论室真实预约，不能沿用校车授权。
6. **AMS 后续交付**：Claude 先做签到码和状态 UI；Codex 等有效课堂码和开放窗口验证本人签到。扫码保持待研究；图书馆座位不进入本期。

## 交接与合并规则

- GitHub PR 和仓库文档是共享事实源；聊天中的结论应由负责该任务的 Agent写回对应能力/验收文档。只报本地完成时必须明确尚未推送。
- 每次开工 fetch，记录 base SHA、相关 PR、负责路径；收工更新本任务的验证与待办。未经声明不同时改同一文件。
- 一个 PR 只做一个主题：原生基础、一个服务 UI、一个服务接入、或回归修复。分支若依赖未合并 PR，明确 base 和依赖；不要 cherry-pick 整套旧 UI。
- 交接必须包含：变更 SHA/PR、稳定公开类型、UI 各状态、运行步骤、验证环境、实际结果、限制和剩余预约。screenshots 不包含登录、乘车码、个人信息。
- UI fixture / preview 必须与真实模式显式分开。不得在运行失败时回退为假预约成功；学校预约不可与演示座位共用 ID 或取消路由。
- 每个 PR 运行 `npm run check`、`npm run build`。UI 补 375/768/1280px、深浅主题、键盘和横向溢出检查；原生补 MuMu 安装与前后台测试。MuMu 结论不标为实体手机或车载扫码通过。
- 不把学校 cookie、token、CSRF、课表 hash、动态乘车码、用户资料或本机解锁信息写入仓库、PR、截图或 fixtures。SSO 由用户在设备登录。
- 本协作计划不启用 dev log；任务状态和交接文档仍按本计划维护。

## 风险与验收

主要风险是旧分支覆盖新 UI、云端看不到本地功能、把假数据当实测、学校 HTML/规则变化，以及临近发车测试留下预约。分别以最新 main 迁移、先发布契约、显式预览模式、失败关闭和优先选择可取消的远期班次处理。写入未知结果先回读本人订单，不自动重试。

交付必须同时有 Claude 的视觉验收材料和 Codex 的真实功能证据，不能用其中一项替代另一项。用户是否采用实体手机、何时测试讨论室多人预约与 AMS 课堂码，由后续可用条件决定，不阻塞当前 UI 工作。
